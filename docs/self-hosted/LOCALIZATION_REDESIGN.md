# 全系统多语言与委员会快照改造计划

状态：范围已确认，待实施。本文件替代此前的设计讨论，作为实施与验收清单。

## 1. 交付目标与范围

完成中文、英文两种界面及委员会语言的分离，消除依靠中文或英文句子存储、识别业务状态的做法。委员会创建时固定语言、国家模板、成员定义和规则内容，源数据更新不影响既有委员会。

沿用 React、Node、PostgreSQL、现有模块和权限模型。覆盖浏览器主应用、代表文件入口、管理页面、服务端、共享契约、历史与归档、Node Agent 和 Rust/Slint 桌面界面。不增加在线翻译服务、通用内容管理层或新的技术栈。

本次不开放委员会内席位改名、alias（别名）、覆盖国家名称或导入目录外成员的新功能；不引入逐席位名称版本体系。不改变投票规则、计时与会期生命周期、席位权限、文件审核及同步语义。

允许破坏性更新，不保留旧字段双写或长期兼容接口。实施前记录当前工作区已有修改，不覆盖其他任务的改动。当前各实施阶段均未开始，本文不作为已完成改造的证明。

## 2. 必须满足的产品规则

### 2.1 语言归属

| 内容 | 显示语言 |
| --- | --- |
| 按钮、菜单、字段标签、帮助、确认框、错误、空态、资源与连接状态 | 个人界面语言 |
| 国家、组织、席位名称；会期、默认发言名单名称 | 委员会语言 |
| 默认决议、修正案、意向性投票标题 | 委员会语言 |
| 文件类型、建议文件名、内置驳回理由 | 委员会语言 |
| 问题类型、会议阶段名称 | 委员会语言 |
| 动议类型的选择项和历史标签 | 界面语言；自定义类型缺少该语言时回退到委员会语言 |
| 正式输出中的系统文案和动议类型 | 委员会语言 |
| 委员会外的模板库、规则库预览 | 界面语言或明确选择的预览语言 |
| 创建委员会时的内容预览 | 所选委员会语言 |
| 用户姓名、委员会名称、主题、正文、自定义标题、自由填写理由、正式文件名 | 原文 |
| 普通界面的日期、数字、单位 / 正式输出中的对应格式 | 界面语言 / 委员会语言 |

系统权限角色标签使用界面语言，会议提交来源中的系统称谓使用委员会语言。包含资源名称的操作提示使用界面句式和已经按委员会语言解析的名称参数，不二次翻译用户原文。

中文委员会使用英文界面时，“Start meeting”与“第1会期”同时出现是正确结果。不得以页面是否含中文作为英文界面的唯一验收标准。

### 2.2 委员会语言

- 创建时必填 `committeeLanguage`，当前支持 `zh-CN`、`en`；创建后不可修改。
- 可选语言为：系统支持语言 ∩ 所用模板支持语言 ∩ 所用规则版本支持语言。
- 模板支持语言根据完整所用国家目录和成员定义的实际名称计算；规则支持语言根据需要显示的规则内容计算。不得仅检查模板标题或未经校验的语言声明。
- 更换待选模板或规则后重新计算交集：原选项有效则保留，无效则清空；交集为空时禁用创建并定位缺失内容。
- 可以默认选择交集中的当前界面语言；无匹配时要求选择，不暗中使用其他语言。界面切换不覆盖用户已选值。
- 创建后新增席位、显式启用其他规则版本仍须支持固定的委员会语言。
- 界面语言独立保存，切换不写入委员会、不改变资源 revision、不丢失表单草稿、不重置计时器或连接。

### 2.3 国家模板与规则隔离

- 创建事务固定所用国家模板的完整目录、所选委员会模板的成员定义和初始配置、规则包完整定义及其文案。
- 源模板、源规则包后续编辑、发布新版、替换默认版本，不自动改变已有委员会。
- 源对象停用或删除不能使已引用的内容失效；当前产品没有的删除入口无需新增，以现有允许操作及数据库生命周期验证此约束。
- 创建后添加席位从固定目录选择，现有成员名称以创建时固定的成员定义为准；不得从实时源模板覆盖名称。
- 暂不开放席位改名或别名，所有创建、更新、批量及其他写入入口均须遵守。
- 主席主动使用现有规则激活/调整功能属于显式委员会操作，继续保留；它产生新的规则绑定或版本，不覆盖创建快照，不追溯修改已发生记录。

## 3. 数据与契约变更

字段名为实施建议；同一含义必须在共享契约、SQL、事件和归档中一致。具体 migration 序号按实施时仓库状态分配。

### 3.1 委员会、模板和席位

| 对象 | 改造内容 | 约束 |
| --- | --- | --- |
| 委员会 | 新增 `committeeLanguage`；保存固定模板内容及来源信息；保留初始规则版本/绑定 | 语言非空、有效且不可更新；来源 ID/revision 仅溯源 |
| 固定模板内容 | 完整国家目录、成员定义、名称翻译、旗帜引用、初始配置；附结构版本 | 创建时写入，普通业务不得覆盖；生命周期随委员会 |
| 席位 | `seatId`、固定定义中的稳定标识、现有权限与排序等可变字段 | 名称和实体身份不能通过更新接口替换；不新增 alias |
| 历史名称 | 席位 ID及固定定义标识；保留现有需冻结的资格等其他事实 | 名称解析不查询当前源模板；停用席位不删除定义 |
| 模板/规则读取模型 | 返回经校验的支持语言及必要来源 revision/version | 服务端创建时重新校验，不信任客户端声明 |

实施选型：优先在现有委员会存储中增加一份固定 JSON 内容，避免跨委员会去重、共享可变模板和逐席位名称版本表。每个委员会只存一份目录，不在每条点名或投票记录重复复制。选择单独表仅在数据库约束或生命周期确有需要时采用，并在实现说明中记录原因。

双语名称属于内容定义，允许含语言文本；业务记录保存稳定标识。`country:cn`、`OPEN` 是机器值，`China`、`Session 1` 不是通用状态。用户原文与正式产物继续原样保存。

固定内容必须能同时表达国家目录条目和委员会模板成员的自定义名称/组织条目。名称来源在创建时解析确定，不依赖旗帜反推实体，也不把模板内已定义的特殊名称误当作委员会内新增别名。

自定义旗帜沿用现有表示；若为内部资源引用，清理源模板不得删除仍被委员会引用的资源。外部 URL 本身不保证远端内容永久不变，不在本改造中无条件下载或复制远端资源。

### 3.2 规则快照

优先复用现有不可变 `rule_package_versions` 和 `committee_rule_bindings`：已发布版本已有禁止更新/删除的数据库约束。阶段 P0 必须验证源包、账号处置、委员会删除和保留策略不会移除其他存续委员会所需版本。

如果现有生命周期无法保证隔离，使用现有规则版本结构保存委员会独立副本；不另建规则执行器。无论采用哪种存储，都必须满足：

1. 执行规则、名称和参数定义一起固定，不只保存包名。
2. 保留创建时绑定；显式规则调整追加新绑定和审计，已有会议资源继续使用其已冻结版本。
3. 历史动议的类型名称来自该动议关联的规则版本，不从当前活动规则版本推断。
4. 归档携带实际所需规则定义，不能只导出一个外部 ID。

### 3.3 自动名称与编号

| 资源 | 保存字段 | 替换的旧行为 |
| --- | --- | --- |
| 会期 | 委员会内固定 `ordinal` | 删除权威 `name`，`nextMeetingSessionName` 改为 `nextMeetingSessionOrdinal` |
| 发言名单 | 现有 `kind`、主题、可选自定义名称 | 不保存默认英文名称作为身份依据 |
| 决议、修正案 | `kind`、固定编号、所属关系、可选 `customTitle` | 不从 `Draft resolution…` / `New amendment…` 解析语义 |
| 意向性投票 | 固定编号、真实 `question` | 不用 `New strawpoll…` 判断是否已填写问题 |
| 文件建议 | 文件类型、提交所属会期序号、建议序号 | 不返回固定中文建议名称作为权威值 |

实施前逐项记录现有编号范围，保持会期内/父文档内等已有归属，不统一成一种全局编号。会期和需要持久编号的资源在现有父对象行锁下分配，保存单调分配状态并设置唯一约束；删除、重排、并发和请求重试不能重号、改号或复用已占用编号。不引入独立编号服务。

`customTitle = null` 表示自动名称；明确提交非空标题表示用户内容，即便它恰好等于默认名称。未编辑的自动标题不能因失焦或保存其他字段被写成自定义标题；恢复默认表达为明确的空值意图。意向性投票问题是否有效由真实字段和现有业务要求决定，不再比较系统生成句子。

文件建议仍是预览，不因此新增正式文件编号唯一性规则；保持当前按提交会期和同类已批准文件数生成建议的语义。批准后正式名称与原始上传文件名分开保存，不随语言变化重新生成。

### 3.4 API、事件与读取边界

- 同步 stage3/stage4 两条创建服务、HTTP 接线、共享请求类型和客户端；即使某入口通常不走，也不能遗漏语言与快照约束。
- 创建请求包含所选语言和实际模板/规则引用；支持预览一致性的地方携带来源 revision。幂等请求摘要包含语言和引用，重试不能额外创建副本或占用编号。
- 委员会更新拒绝 `committeeLanguage`；席位更新拒绝 `displayName`、alias 和身份标识变更。新增席位提交固定目录标识，由服务端验证并解析。
- 列表、工作区、公开快照、代表 bootstrap、相关 Agent 响应带足够语言和名称上下文。派生显示名可以为读取便利返回，但不得作为写入或业务判断依据。
- 只给 Owner/Chair 返回选择席位所需的完整目录；公开和代表读取只返回其授权内容需要的名称与语言，不把整个私有模板或规则定义扩散到低权限响应。
- 事件、审计、幂等缓存和实时刷新同步新字段。事件保存类型、参数和固定定义引用；正式用户内容可以保存原文，不拼接依赖操作者界面语言的业务事实。
- 更新 schema compatibility、契约及归档版本；Agent 协议仅在实际不兼容字段变化时升级。

## 4. 创建流程与一致性

1. 读取候选模板和规则，计算并展示语言交集及所选语言下的预览。
2. 提交时沿用现有权限、来源校验、幂等和事务机制。
3. 在一致的数据视图中读取模板主记录、子条目和规则版本；使用现有锁/revision 约束避免混合不同修改时刻的数据。
4. 服务端重新计算交集，拒绝已失效语言；若来源已改变使预览失效，返回可定位冲突，要求刷新后重选。
5. 同一事务创建委员会、固定内容、初始规则绑定、席位、事件及审计。任何一步失败全部回滚。
6. 数据库限制委员会语言和固定内容的普通更新。历史迁移/受控永久删除按现有专用机制处理，不为业务 API 开后门。
7. 创建后所有名称读取和新增席位路径只用委员会固定内容；管理员更改默认模板/规则仅影响之后的创建。

## 5. 显示、错误与文件处理

### 5.1 显示层

- 按 identity、committee、proceedings、files、system 等现有领域拆分文字目录，使用稳定词条标识和命名参数，避免整段英文或字符串拼接承担业务含义。
- 提供明确的界面文案和委员会内容格式化入口；委员会内容必须显式获得语言与固定定义，不从全局界面语言猜测。
- Web 与 Node 复用语言无关类型及需要一致的纯格式化逻辑；不引入 React 到服务端依赖。桌面使用对应目录和错误定义，避免另一套名称规则。
- 将 `LanguageProvider` 的整棵子树 key 重挂载改为订阅语言变化；同步处理第三方组件默认文字，保留表单、焦点、选中资源和业务连接。
- 移除 `localizeGeneratedName` 的正则和字符串集合推断；同步导航、编辑输入、选择器、当前内容和历史分隔标题。
- 时间戳、时长、字节数仍保存原单位数值；显示用指定语言格式化，时区及 B/KB/MB/GB 的现有业务换算规则保持不变。
- 中英文词条、命名参数及必要复数形式有完整性检查；内置模板和规则文案双语完整。用户内容不做机器翻译。

### 5.2 错误与身份

错误契约保留通用 `code`，增加具体 `reason`、受约束 `params`、`fieldErrors`（field/reason/params）。客户端依此选择界面文案；不按服务端 message 匹配错误类型，不将未知内部异常直接展示。

字段错误须标红、说明原因、展开并定位；未知错误提供本地化通用提示和 requestId。身份 API、业务 API、上传通道及桌面桥接都使用对应处理，不只修改普通 fetch。

系统身份使用状态或来源代码，例如 ANONYMIZED、CHAIR；真实姓名和用户自定义称谓保留原文，不用“匿名账号”“主席”等固定中文冒充姓名。

### 5.3 文件与驳回

- 文件建议按类型和数字在委员会语言下展示；确认后的正式文件名、下载名称、原始上传名和 Agent 路径不随界面语言改变。
- 内置驳回类型使用稳定 ID 和双语定义；自定义配置沿用多语言内容形式，保存/使用时验证委员会语言可用。
- 创建时复制的默认驳回配置也必须能用于所选委员会语言；若缺失，返回明确配置错误，不静默引入其他语言。
- 拒绝时冻结所用定义/参数或实际确认原文，之后编辑选项不改写旧理由；自由填写理由直接保存。
- 文件审核、代表端历史和实时事件采用一致的名称与原因解析。语言改造不触发重命名磁盘文件、重新上传或重新配对。

## 6. 历史、归档和资源清理

- 历史点名、发言、问题、动议、投票、文件提交者等名称统一使用该委员会固定定义；保留既有资格和规则冻结边界。
- 归档包含语言、固定国家/成员定义、实际使用规则版本、资源编号和用户原文；在源模板不可访问时仍可独立解释名称与规则。
- 同步检查显式 SELECT 列表，尤其 meeting_sessions、speaker_lists、documents 和新固定内容，避免数据库新增字段而导出遗漏。
- 删除委员会时，在历史引用和相关文件处理完成后清理其固定内容；只删除该委员会拥有且无其他引用的数据，不能删除共享的存续规则版本。
- retention、源模板清理、账号处置及内置数据升级都不得改写委员会副本或破坏其内部资源引用。
- 新数据以统一标识写入；此次破坏性升级不要求从来源不明的旧字符串恢复其自动/自定义意图，也不批量改写既有不可变审计记录。

### 8.2 浏览器与桌面验收

中文/英文委员会各使用中文/英文界面，共四种组合；同一委员会至少两个不同界面语言的查看者同时核对。覆盖上述页面清单的主要正常、空、失败和历史状态。

重点手工检查：语言切换保留未保存输入与焦点、当前计时器不中断、动议名称回退正确、设置与点名的国家名一致、文件审核建议语言正确、长英文布局与无障碍标签完整。出现用户中文原文不视为漏翻。

Agent 和桌面需要单独运行验证，不以 Web 测试或桥接 mock 代替；未能运行时明确记录阻塞原因和未完成项目。

### 8.3 仓库验证入口

所有项目命令先执行：

```sh
source scripts/wsl-env.sh
```

按阶段运行受影响的契约、HTTP、页面和真实 PostgreSQL 集成测试；最终执行现有总入口：

## 9. 破坏性升级与完成标准

### 9.1 升级步骤

1. 实施时重新检查 Compose 项目及运行镜像，明确目标本机开发实例；不从默认项目名推断，也不在文档中固化当前容器状态。
2. 先在隔离环境验证新库建库及迁移链。历史 migration 不改写，新增迁移；非空旧库不尝试猜测旧标题来源，提供明确的不兼容提示或已定义的重建路径。
3. 明确重建范围和操作顺序。仅移除目标实例需要重建的数据，不使用无差别卷删除；保留与变更无关的账号/设备配置和目录。若委员会被删除导致旧配对失效，按实际依赖说明并重建对应关系，不承诺旧配对仍可用于已删除委员会。
4. 停止目标实例旧业务写入，执行限定范围重建，构建并重新创建应用容器；后端和数据库更新不能仅依赖 Vite 热更新或 Docker start。
5. 使浏览器及受影响 Agent 使用匹配版本，清除或失效处理旧契约缓存；验证 readiness 后导入验收数据，执行四种语言组合及文件流程。
6. 记录部署版本、数据库版本、执行检查及未完成项。重建后不能仅回滚应用镜像到旧数据库契约；如需退回，应使用配套版本和对应开发数据库。
