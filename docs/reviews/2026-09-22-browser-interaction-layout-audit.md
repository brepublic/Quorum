### 01 · P1 · 人工计票快速输入后查看结果，会冲突并覆盖未保存票数

**位置：** 意向性投票人工计票页。本轮在中文界面复现。

**步骤与结果：**

1. 新建题目和 A、B 两个选项，创建人工计票。
2. 把 A 填为 8，随后把 B 填为 7，紧接着点击“查看结果”。
3. 页面一度显示“状态已更新，请重新载入后重试”，仍停留在计票页；A 为 8，B 回到 0。
4. 重新填写 B 为 7，点击标题使其保存，再单独点击“查看结果”，才进入正确的 8／7 结果页。

**影响：** 用户输入可能被刷新覆盖，不能依赖一次正常的填写和提交得到完整结果。

**原因定位：** `ProceedingsPanel.tsx:1411–1417` 在各输入框失焦时保存票数，“查看结果”又独立提交阶段切换，前一次保存尚未完成并刷新时，两者可能携带同一版本号。服务端每次票数保存递增版本；`1305–1310` 在版本更新时又把所有输入重置为服务器值。正常的输入顺序即可让这些请求互相冲突。`CommitteeWorkspaceContext.tsx:74–92` 未将请求串行化，服务端 `server/src/modules/stage5/service.ts:2800–2801,2839–2852` 对写入检查并递增版本。

**建议：** 在现有组件内串行保存；查看结果前先完成未保存票数，再以最新版本切换阶段。提交中锁定相关操作，失败时保留输入；刷新不能覆盖仍在编辑的字段。无需新增服务。

**复核：** 中英文快速输入多项后立即查看结果；上一项响应返回时继续编辑下一项；出现保存失败时输入仍保留且不进入错误结果。

**证据：** [冲突后的 A8／B0](../../outputs/ui-audit-2026-09-22/zh-poll-count-conflict.jpg)、[分开保存后的 8／7](../../outputs/ui-audit-2026-09-22/zh-poll-result.jpg)。冲突提示曾短暂出现，保存的静态记录主要证明票数回退。

## 按钮语义与复用建议

颜色、实心／描边、尺寸与分组应表达操作层级，不必让所有按钮外观完全相同。建议以现有设计为基础形成下列约定，再按具体页面小范围修复。

| 操作含义 | 建议沿用的表现 | 本轮观察 |
| --- | --- | --- |
| 保存、创建、当前主要提交 | 蓝色实心，有明确动作文字 | 大部分表单已有此模式；模板成功提示需要正确跟踪当前草稿 |
| 批准／通过与驳回／未通过 | 绿色／红色，互斥成对时等宽分组 | 动议和文件审核已有较好一致性；不把连体按钮本身视为间距缺陷 |
| 删除、撤销权限等危险动作 | 红色；最终确认说明具体目标 | 页面内删除通常可识别，但确认方式仍有两套，见下节 |
| 编辑、返回、取消、重新打开 | 中性或描边，视觉弱于主要动作 | 人工计票的“编辑选项／查看结果”分组可以保留；保存顺序必须修正 |
| 计时开始／暂停／继续 | 相同动作词、图标及状态反馈 | 自由磋商需要与发言计时统一 |
| 状态信息 | 文字＋必要图标／颜色，不伪装成操作 | 问题结果与文件引用需要统一 |
| 独立相邻动作 | 明确间距；小屏可换行 | 国家模板添加／保存间距为 0，决议表决 Undo 缺少换行空间 |

可优先复用现有 CSS、Semantic UI 控件及状态样式。只有出现真正重复的完整结构时才考虑抽取小组件；本报告不建议建立新的全局设计系统。
