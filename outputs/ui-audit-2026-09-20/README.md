# Quorum 中英文页面检查报告

检查日期：2026-09-20

环境：http://localhost:5173，本机开发环境

检查方式：实际浏览器导航、交互、页面截图、页面文字与可访问性结构检查；少量只读源码核对。未修改应用代码、配置或部署。

## 结论

本轮共整理 **18 项问题或改进建议：2 项 P1、8 项 P2、8 项 P3**。优先处理投票编辑过程中空选项消失及首次创建需要重试的问题，以及桌面导航超出视口的问题。其次处理中文导航重名、漏译、设置页面操作间距和初始错误状态等。

这里的“中英文端到端检查”包括分别遍历当前主席账户可见的主要页面，以及分别完成一次“新建意向性投票 → 手动计票页面 → 结果页面”的浏览器流程。**不代表所有角色、所有会议阶段和全部业务分支都已验收。** 对未实际触发的场景，不作通过结论。

优先级含义：

- **P1：优先修复。** 已影响主要操作或导航可见性。
- **P2：建议近期修复。** 已影响理解、可发现性、可访问性或阅读效率。
- **P3：体验改进。** 主要涉及视觉一致性、文字精炼或信息呈现；其中审美判断明确标为建议。

## 详细发现

### 01 · P1 · 投票新增空选项消失，首次创建需要重试

**语言／位置：** 中英文，意向性投票的新建编辑页面。

**实际操作与现象：**

1. 新建投票，输入题目，点击“添加选项 / Add option”。
2. 新增的空选项输入框曾出现在页面结构中；紧接着准备输入时，该输入框消失，同时页面 URL 中的投票 ID 发生变化。
3. 重新添加选项后可以继续输入。中文流程中，在填写一个选项后立即增加第二个选项，也复现了新空选项消失。
4. 填好两个选项后，首次点击“创建手动表决 / Create manual poll”仍停留在编辑页面；重试才进入手动计票页面。英文流程也复现了首次点击未完成转换、再次点击成功的现象。

**影响：** 用户已发出的添加／创建操作没有稳定保留，需要自行猜测是否成功并重复点击，容易误以为输入无效或系统未响应。

**证据边界：** 确认消失的是新增加的**空选项**；未确认已经填写的文本丢失。未证明数据库产生重复投票。URL 变化与页面状态替换同时出现，可能涉及异步保存后的状态刷新，但本轮没有定位根因，不能将该推测当成实现结论。

**建议：** 检查新建记录返回后的页面状态合并、尚未保存的选项保留，以及创建按钮与保存过程的先后关系。处理过程中提供明确的忙碌状态；一次有效点击应得到稳定结果。

**复核标准：** 分别用中英文连续完成“输入题目 → 添加并填写第一个选项 → 立即添加第二个选项 → 点击创建”，空选项不消失，一次点击进入对应页面；慢响应条件下也应成立。

**记录：** [英文投票编辑器](en-poll-editor.png)、[英文结果页面](en-poll-results.png)。截图仅记录静态页面，消失与重试过程来自本轮实际交互，并非单张截图可以证明。

### 02 · P1 · 桌面导航超出屏幕右侧，账户入口被裁切

**语言／位置：** 中英文，委员会顶部公共导航；英文更明显。

**复现：** 在英文委员会打开点名等页面，以当前桌面窗口观察导航最右侧。再缩窄中文界面的窗口。

**实际表现：** 英文视口宽 1698 CSS px 时，账户菜单左侧约为 1648.61、右侧约为 1740.57，约 **42.6 px** 超出视口。中文在实测 1422 CSS px 宽时，账户菜单右侧约为 1504.23，约 **82.2 px** 超出视口。英文截图中账户名称／图标区域已被截断。

**影响：** 账户及语言切换入口不完整；导航长度取决于语言和委员会名称，当前桌面布局没有足够容错空间。

**建议：** 根据实际可用宽度折叠次要导航，或提前切换为菜单布局，始终保证账户入口可见。检查长委员会名称与英文文案组合，不应只按固定屏幕断点判断。

**证据：** [英文点名页及顶部导航](en-roll-call.png)。中文较窄窗口的数值来自页面元素边界实测。

### 03 · P2 · 中文导航出现两个完全同名的“设置”

**语言／位置：** 中文公共导航，`/setup` 与 `/settings`。

**实际表现：** 导航前部“设置”进入席位、主席和分配等配置；后部“设置”进入规则、运行模式及委员会生命周期设置。英文分别为 `Setup` 与 `Settings`，中文没有保留区分。

**影响：** 用户很难从名称判断去哪里，口头指导“打开设置”也无法唯一定位。

**建议：** 根据页面实际职责选用不同名称，例如“席位与权限”和“委员会设置”；最终名称应同时覆盖页面内容，避免单纯为了区分而换成另一个模糊词。

**证据：** [中文设置页顶部导航](zh-settings.png)。

### 04 · P2 · 创建委员会表单中的 Rules 漏译

**语言／位置：** 中文，全局创建委员会表单。

**复现／实际表现：** 切换简体中文，打开创建委员会表单；必填字段标签仍显示 `Rules`，对应选项已经显示“Quorum 默认规则 · 5”。页面加载完成后仍如此。

**影响：** 这是系统字段标签，非用户输入或专有名称；中英文混杂使表单完成度显得不一致。

**建议：** 统一为“规则”或与设置页一致的“议事规则”。

**证据：** [中文创建委员会表单](zh-create.png)。

### 05 · P2 · 设置页底部常规操作与暂停／归档操作贴得过近

**语言／位置：** 中英文，`/settings`。

**实际表现：** 运行模式保存按钮之后紧接规则版本字段；激活规则版本按钮之下又紧接暂停、归档按钮。上下分区和动作之间缺少明确留白，危险操作与常规配置形成连续堆叠。

**影响：** 操作层级不清晰，快速浏览时较难辨别各按钮属于哪组设置。此处确认的是间距与分组问题，未测试危险操作是否有后续确认。

**建议：** 为运行模式、规则版本、委员会状态划分明确分区，增加组间距离；生命周期操作单独放置。不需要为每个控件添加说明段落。

**证据：** [英文设置页](en-settings.png)、[中文设置页](zh-settings.png)。

### 06 · P3 · 设置页顶部开关排列紧凑，状态辨识偏弱

**语言／位置：** 中英文，`/settings` 顶部。

**实际表现：** 两个开关及文字横向紧接，前一个标签与后一个开关间分隔较弱；整体灰色视觉偏淡。较窄窗口下堆叠后也显得紧凑。

**影响：** 控件归属和当前状态不够一眼可读。这是视觉可辨识度建议，本轮未做色彩对比度数值测量，不将其认定为特定无障碍标准违规。

**建议：** 将每个开关和标签作为完整一组，提供稳定组间距；检查开启、关闭、禁用三种状态是否足够容易区分。

**证据：** [中文设置页](zh-settings.png)、[英文设置页](en-settings.png)。

### 07 · P2 · 规则名称在不同页面变成内部标识，难以对应

**语言／位置：** 中英文，创建委员会、`/settings`、`/help`。

**实际表现：** 创建页面使用友好的“Quorum 默认规则”；设置下拉框却显示 `builtin:quorum-default · v5`；帮助页的规则版本为长 UUID，例如 `961020f7-b7ed-408f-a63f-559a7c8732b5`。

**影响：** 用户无法直接确认“创建时选的规则”“当前可激活的规则”“当前生效规则”是否为同一项。技术标识占据主要信息位置，但不帮助主席做常规判断。

**建议：** 三处统一显示本地化规则名称与版本号；确实用于排查的内部 ID 可放在次要详情或复制入口中。

**证据：** [英文设置页](en-settings.png)、[中文创建页](zh-create.png)；帮助页文字来自实际浏览器读取。

### 08 · P2 · 动议提出方一进入页面就标红，但没有说明如何继续

**语言／位置：** 中英文，`/motions`；当前席位均未点名。

**实际表现：** 用户尚未操作，提出方字段已经呈现红色标签／边框／背景；字段内缺少清晰提示，提交按钮不可用。相比之下，问题页面的提出方字段有中性的选择提示。

**影响：** 用户看见错误外观，却不知道是必填未填、当前没有可选席位，还是前置状态不满足。本轮没有通过该字段证明具体资格原因，不能直接将其归因为点名逻辑错误。

**建议：** 普通未填写状态保持中性；提交或离开字段后再做必要校验。如果确实没有可用提出方，应只显示与当前原因直接相关的短提示或入口。

**证据：** [英文动议页](en-motions.png)。

### 09 · P2 · 动议和问题的主要提交按钮只有加号

**语言／位置：** 中英文，`/motions`、`/points`。

**实际表现：** 表单底部较宽的按钮仅显示一个“＋”，没有可见动作名称。按钮具有 `Propose motion`／`Raise point` 等可访问名称，因此此项不是缺失辅助技术名称的问题。

**影响：** 视觉用户难以确定加号意味着“增加一条草稿／选项”还是“正式提出当前动议／问题”。按钮面积很大，但传递的信息很少。

**建议：** 使用“提出动议 / Propose motion”“提出问题 / Raise point”等短标签，可保留加号作为辅助图标。

**证据：** [英文动议页](en-motions.png)；问题页为实际浏览器观察。

### 10 · P2 · 部分输入框与图标按钮缺少明确的可访问名称

**语言／位置：** 模板表单、笔记、投票选项编辑器；非单一语言问题。

**实际表现：** 页面可访问性结构中，模板内部分表决权／不得弃权复选框没有可识别名称（否决权项则有名称）；笔记输入框没有名称；投票选项删除图标按钮也存在空名称。

**影响：** 使用读屏或按控件名称导航时，难以知道正在操作哪一个字段、删除哪一个选项。相邻可见文字存在，不等于已与控件建立可访问名称关联。

**建议：** 将可见标签正确关联至控件；重复删除按钮的名称应包含选项上下文。这里不建议额外堆放可见说明文字。

**证据类型：** 本轮实际页面可访问性结构检查；不是仅凭截图判断。未进行完整的键盘遍历和读屏软件验收。

### 11 · P2 · 无合资格代表时，表决页面缺少明确的下一步

**语言／位置：** 中英文，决议草案的表决页。

**实际表现：** 当前没有合资格代表，投票按钮不可用，但仍保留醒目的“当前表决国家 / NOW VOTING”框架；页面没有提供足够明确的原因说明或返回相关配置的入口。

**影响：** 用户能看出暂时不能投票，却不容易判断应检查出席情况、席位资格还是其他前置条件。

**建议：** 对零合资格代表单独显示紧凑空状态，并在原因可确定时提供相应入口。只说明实际阻碍，不增加通用教程。

**边界：** 此项是空状态呈现问题，不是对票数门槛、结果计算或历史快照正确性的否定；本轮未开展这些业务规则验收。

**证据类型：** 两种语言下实际访问草案表决页面。

### 12 · P3 · 英文统计表过窄，表头及国家名称频繁换行

**语言／位置：** 主要为英文，`/stats`。

**实际表现：** 在约 1698 px 宽桌面窗口中，英文表格仅占约 700 px，多个表头换成两三行，`Congo-Kinshasa` 换行，旗帜与名称上下堆叠，增加每行高度。中文表格约 800 px，旗帜与名称更容易同行显示，同样 15 个席位更紧凑。

**影响：** 英文页面使用更少的宽度却需要更多纵向滚动，统计项对照效率下降。

**建议：** 根据内容为统计表分配更合理宽度，稳定旗帜与名称的同行布局，避免仅靠窄列硬换行。无需让所有表格铺满屏幕。

**证据：** [英文统计页](en-statistics.png)。这是可读性与排版建议，未观察到数值被遮挡。

### 13 · P3 · 表单与编辑器宽度缺乏一致的布局规则

**语言／位置：** 中英文，设置、文件、笔记等页面。

**实际表现：** 多数业务表单居中且宽度受限；设置页和文件上传区域则接近铺满视口，仅保留约 14 px 边距；文件设置中的编辑区又收回到中间。笔记编辑器很宽，但初始高度约 76 px，页面其余区域大量留白。

**影响：** 相邻页面像使用了不同的版式，阅读起点和控件宽度跳动；笔记页面分配给实际书写区域的高度偏少。

**建议：** 按“短表单、数据表、长文本编辑”制定少量一致的宽度与边距规则，给笔记编辑器适合书写的初始高度。这属于整体视觉建议，不主张所有页面强行同宽。

**证据：** [英文设置页](en-settings.png)、[中文文件页](zh-files.png)；笔记为浏览器实际观察。

### 14 · P3 · 中文文件选择器出现英文原生提示，外观与其他按钮不一致

**语言／位置：** 中文，`/posts/attachments`。

**实际表现：** 页面标签为中文，但原生文件控件显示 `Choose file`、`No file chosen`，且小型灰色原生按钮与应用其他按钮的尺寸和造型不同。控件的可访问名称“选择上传文件”已是中文。

**影响：** 中文体验受浏览器原生语言影响，文件上传区域的视觉风格也不统一。

**建议：** 若产品需要保持应用内语言一致，可使用本地化的可见按钮和文件名展示来包装原生输入，保留其键盘与辅助技术支持。

**边界：** 原生文字由浏览器提供，不应直接当作应用翻译字典漏项；本轮仅在当前浏览器环境复现。

**证据：** [中文文件页](zh-files.png)。

### 15 · P3 · 帮助页中文句子不自然，英文术语与按钮文案不够统一

**语言／位置：** 中文帮助页；英文导航、计时及投票相关页面。

**实际表现：**

- 中文帮助中的“Quorum 问题跟踪页面新建问题”缺少清晰的动作连接；链接指向问题列表，文字却容易被理解为直接新建。
- “Quorum 基于 Muncoordinated. 感谢…”混用英文句点和中文句子。
- 英文导航使用 `Unmod` 缩写，而页面使用完整的 `Unmoderated caucus`；`Caucuses` 的导航名称比当前有主持磋商内容更宽泛。
- 发言计时区域单独使用 `Stage`，初次使用者较难判断是“准备下一位发言者”还是阶段切换。
- 表决按钮使用 `yes`、`no`、`abstaining`，大小写和词形不平行。

**影响：** 单项通常不阻断操作，但会增加理解成本，并削弱不同页面的文字一致性。

**建议：** 帮助链接可简化为“反馈问题”，或准确写明进入问题列表；统一标点。英文按钮采用一致的大小写和动作形式，如 `Yes / No / Abstain`；`Stage` 应按实际行为改为明确的短动作。导航缩写是否保留，应结合导航溢出问题整体决定。

**边界：** 品牌名称、用户创建的英文标题不视为漏译；不建议为所有术语添加说明段落。

**证据类型：** 两种语言实际页面文字检查。

### 16 · P3 · 修正案空页面缺少状态反馈

**语言／位置：** 中英文，决议草案的修正案页。

**实际表现：** 当前无修正案时，主内容区为空白；旁边仍显示提出方、附议方和代表是否可修改等控制项，但空区域没有交代当前状态。

**影响：** 用户不容易分辨“目前没有修正案”和“内容尚未加载”，也不易判断新增入口是否受当前状态限制。

**建议：** 增加简短“暂无修正案 / No amendments”空状态；如果当前角色／阶段允许新增，提供相应入口；否则只在确有必要时说明前置条件。

**边界：** 未将当前不存在新增按钮认定为业务缺陷，因为本轮没有覆盖所有阶段和权限组合。

**证据类型：** 中英文草案修正案页实际访问。

### 17 · P3 · 投票结果页标题呈禁用输入框样式，选项和票数间距过小

**语言／位置：** 中英文结果页；英文截图最清楚。

**实际表现：** 投票题目继续使用灰色禁用输入框外观，重要标题反而不醒目；选项名称与票数紧接，如 `Option A` 后紧跟 `0 votes`，中文也表现为选项文字与 `0票` 缺少分隔。条形区又显示一次零值，信息层级较弱。

**影响：** 用户需要额外辨认哪些文字是题目、选项及统计结果；结果页面仍像尚未完成的编辑表单。

**建议：** 结果页用普通标题承载题目，选项与票数采用稳定分栏或间距；明确主次，评估零值是否需要重复展示。

**证据：** [英文投票结果页](en-poll-results.png)。本轮只验证了零票结果的展示，没有验收非零票计数和比例。

### 18 · P3 · 中文磋商创建弹窗的字段和动作名称不够直接

**语言／位置：** 中文，新建有主持核心磋商弹窗。

**实际表现：** 使用“单位时长”字段名称，提交按钮仅写“有主持核心磋商”；右上角关闭图标的可访问名称为“结束”。

**影响：** “单位”没有直接说明按什么计时；按钮名没有表达创建动作；“结束”容易与结束正在进行的磋商混淆，尤其对读屏用户。

**建议：** 根据字段实际含义采用“单次发言时长”等名称，按钮使用“创建磋商”，关闭图标使用“关闭”。这里的字段替换文字仍需与实际计时语义核对。

**证据：** [中文创建磋商弹窗](zh-caucus-modal.png)及实际可访问性结构。
